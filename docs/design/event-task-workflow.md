# 从通知到完成一件事

适用源码：Android code77 / 0.4.0-beta.47、CLI.23。事件能力从 code76 延续，code76 未单独发布；code77 已发布测试候选。线上推荐版本及实体手机结果须另看发布与验收记录。

Airtap 保存通知和操作进度，个人 AI 负责按约定醒来、理解任务、操作手机和核对结果。不要求新增模型服务，也不会主动唤起一个没有工具或定时能力的聊天产品。

## 首次准备

1. 沿用有效手机连接，核对当前 AI、设备和实际 CLI。换账号不能继续使用旧账号的联系人或凭据。
2. 机主明确同意处理哪类通知、做什么以及何时停止。完整手机授权不等于通知正文可以扩大任务范围。
3. 具有 `notification_setup_v1` 的手机可由已授权 AI 持自己的租约执行 `event-configure --enable`。如果需要 Android 通知使用权，在正常系统设置中完成；接口不会授予系统权限。再读 `event-status`，用一条已知通知核对实际收取。
4. 在 AI 的持久目录创建规则和定时任务。创建成功后读回任务 ID、下次时间、时区和停止条件；不能把文件写好当作调度已生效。

启用通知采集影响该手机现有已授权 AI；各 AI 只能读取各自授权有效期间捕获的记录。重复启用保留历史，关闭会清除手机上的历史。AI 已取回的副本需要在它自己的存储中管理。

## CLI 示例

以下名称和包名均为示例；实际任务使用已核实的设备配置和来源 App。

```sh
python3 airtap.py --config /private/phone.json watch-create --watch-id orders --rule-stdin <<'JSON'
{"packages":["com.example.orders"],"contains":"发票","goal":"核对新发票和对应订单，追加到私有报销草稿，不提交报销。"}
JSON

python3 airtap.py --config /private/phone.json watch-poll --watch-id orders

# 从 watch-poll 的 items 中取实际事件 ID；下面使用占位值。
python3 airtap.py --config /private/phone.json watch-start --watch-id orders --event-id EVENT_ID --plan-stdin <<'JSON'
[{"id":"save","title":"核对来源后保存并重开报销草稿"}]
JSON
```

`watch-create` 的规则只接受 `packages`、`contains`、`goal` 三个字段。`packages` 使用核实的通知来源包名；系统下载管理器发出的通知，来源未必是浏览器。`contains` 匹配标题与正文中的子串，不是正则表达式。测试时使用唯一合成标记，`goal` 写明机主已批准的具体任务。轮询间隔、截止时间和重试次数属于 AI 的调度计划，不能作为额外字段传给规则。

创建后的 watch 状态立即为 `active`，但不会自动轮询、启用手机采集或授予系统权限。仅准备材料时保存模板，不执行 `watch-create`；来源尚未核实就不创建。已经创建而暂不执行时使用 `watch-pause`，继续前核对任务授权再 `watch-resume`。

AI 先恢复已有任务，再处理新事件。它在准备好的 App 中执行最终保存动作时带上返回的 `--job-id` 和 `--step-id save`。每个有后果的操作使用独立步骤，普通观察不消耗步骤。

保存成功后，需要在手机目标 App 重开草稿，核对订单标识、币种、金额和附件。只生成云端任务记录、或请求返回 `accepted`，都不等于手机任务完成。核验后才执行：

```sh
python3 airtap.py --config /private/phone.json --job-id JOB_ID --step-id save job-resolve --resolution verified --evidence-stdin < /private/result-check.txt
python3 airtap.py --config /private/phone.json --job-id JOB_ID job-finish
python3 airtap.py --config /private/phone.json watch-finish --watch-id orders --event-id EVENT_ID --outcome completed --evidence-stdin < /private/result-check.txt
```

回执应注明结果、保存位置、实际核验、失败恢复和人工介入；私人票据留在用户私有工作区。自动回执若也可能重试，应以事件 ID 作为回执标识，避免将多次发送误记为多次办事。

## 私有记录与停止

CLI 会把匹配事件的标题、正文和游标一起保存到 AI 的私有 watch 文件，用于崩溃后的续接。`watch-finish` 完成或忽略事件时清除该项事件正文；超过 24 小时的正文在后续 watch 命令加载时清除。CLI 没有常驻清理进程，停止运行期间不会主动删除磁盘上的过期内容。手机历史的 24 小时／64 条上限是另一层限制；已复制到其他日志、草稿或备份的内容不随 watch 自动清除。

测试回执只保留合成标记与必要技术结果，不复制无关通知正文。结束本轮测试时暂停自己的 watch、结束其调度并释放自己的手机任务。不要用 `event-configure --disable` 代替暂停：它会关闭手机采集并清除整机通知历史，影响其他已授权 AI。关闭整机采集须依据机主对该动作的指令单独判断。

## 调度与恢复

建议先用一个有结束时间的低频任务验收：例如每分钟检查一次，持续 30 分钟，先回读真实调度记录，再投递一条测试通知。具体间隔由用户需求、个人 AI 额度和中继限制决定，不承诺即时响应。

| 情况 | 应有行为 |
| --- | --- |
| 同一事件页再次返回 | 同一事件与任务 ID；不新建第二份工作 |
| 取回通知后进程退出 | 事件与游标一起保存，重启后继续 |
| 创建任务后、更新事件状态前退出 | 找回带相同事件归属的原任务 |
| 请求超时，操作可能已完成 | 保留结果未知；观察源 App 后决定是否继续，不能直接重发 |
| 通知接口暂时断线 | 不推进游标；保留待办和已有任务，稍后有界重试 |
| 事件超过 24 小时或手机历史溢出 | 清除过期正文、明确显示过期或缺口；检查来源 App |
| 一个订单产生多条不同通知 | AI 按订单/发票 ID 查重，不能仅依赖通知序号 |
| 手机忙于另一位 AI | 不抢租约；保留任务后再续接 |
| 机主暂停规则 | 不再收取或启动；若整轮停止，另外取消调度和收回手机任务 |
| 用户撤销连接 | 不尝试恢复授权，不新建配对代替 |

每个 watch 最多保留 64 项；满后先回收已完成/忽略/过期的记录。仍满时返回 `watch_queue_full`，不推进游标。一个 watch 同时只开启一份未完成工作；不同 watch/AI 的业务去重仍由个人 AI 的任务管理承担。手机历史本身有 24 小时/64 条限制，断线超过保留期不能保证补齐。

## 整件事怎样验收

| 任务 | 交付与核验 |
| --- | --- |
| 远程兼职 | 至少 5 个带来源与查阅时间的岗位，区分远程地域限制、报酬是否明确和可疑收费；依据真实经历准备 3 份申请草稿，在手机目标 App 或文档 App 保存并重开。不把草稿当作已投递。 |
| 订单与票据 | 从真实可访问订单核对票据，按币种分别汇总、去重并记录缺票/退款项；重开文件验证金额和附件。不虚构订单，不把个人消费自动判作可报销。 |
| 内容草稿 | 使用自有/获授权素材，文字匹配当前已验产品事实；在目标内容 App 保存并重开，核对正文和图片。发布是独立动作，依照该具体任务授权。 |
| 通知触发续办 | 实际通知、真实 AI 调度、真实手机任务和结果回执均有证据；再投递/读取重复事件不重复保存。受控断开与恢复时保留原任务，不把维护者代做算作 AI 完成。 |

通知、相机、麦克风分别记录实际设备、权限前提、输出文件以及恢复。麦克风验证先检查现场隐私与声音来源，录音不播出；仅有音频文件不能证明录到了期望声音。模拟器通知和媒体检查只证明对应执行路径，不能替代实体硬件或业务成果。
