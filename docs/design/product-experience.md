# 从安装到真正办完一件事

产品目标是让用户把事交给自己的 AI，然后得到可核对的结果。评审不以功能数量、按钮数量或一次演示成功为结论。当前 Android 主线保留八位邀请、六位核码、有效连接恢复和已有 AI 代办管理。

## 这一轮改什么

| 使用阶段 | 观察到的问题 | 改动与判断依据 |
| --- | --- | --- |
| 决定试用 | 用户需自己理解“工具能力” | Muse、Instinct 走默认安装步骤；其他 AI 有可复制的实际检查请求。网站不伪装成检测器。 |
| 邀请与核码 | 容易以为还需回聊天说“已点” | 邀请说明要求 AI 自行查批准状态，复用现有有界等待。首次核码批准保留。 |
| 连接之后 | 配对成功容易被当成体验完成 | 提供一件跨 App 任务，要求保存、重开、核对并报告位置；复制不执行、不标记完成。 |
| 日常打开 App | 多 AI 页偏连接管理，恢复状态不突出 | 先显示真实连接状态；有效租约显示当前接手的 AI，详细管理收起，停止仍可见。 |
| 遇到问题 | 容易变成重配或叫用户来解锁 | 原连接保持；分别说明自动恢复、准备屏幕和实际系统验证，不笼统要求所有情况本人处理。 |
| 了解产品 | 首页与 README 混有大量版本细节 | 默认先读用途、安装、结果；工程记录可展开或跟链接查看。隐私事实继续直接展示。 |

Android 界面改动属于 code77 候选，不等于推荐版已切换。网站可使用当前 APK 做独立内容刷新，不改变手机和中继版本。已有观察与真实验收按原范围继续，不因本轮体验评审重新计时。

## 走查与可点击体验

直接使用本次实现的安装页作为可点击体验，不另建一套无法交付的假界面。依次完成：下载入口 → 可选 AI 检查 → 安装步骤 → 首件任务复制 → 失败帮助 → 再次使用。

逐步记录：用户此时知道什么、想完成什么、下一步是否可见、动作后是否得到真实反馈。检查 320、390、768、1440 像素宽度、键盘焦点、无 JavaScript 的正文可读性，以及复制失败时的手动选择路径。按钮“已复制”只说明剪贴板写入成功，不能呈现“连接成功”。

Android 用隔离模拟器检查真实组件：连接、恢复、系统验证、任务持有人过期、首件任务复制。不得删除 `FLAG_SECURE` 或改生产手机设置来取演示画面。模拟器与维护者走查不是独立用户试用。

## 独立用户试用

首轮找 3–5 位未参与开发、已有可用个人 AI 和 Android 14+ 手机的用户，按各自入口分别记录。不把小样本当作总体成功率。暂时没有人选时保留“未开展”，技术检查照常推进，不编造试用结论。

给参与者的任务只有：“让自己的 AI 把网页上的三条公开资料整理到手机便签，保存后重新打开核对。”提供正常安装页，不先解释邀请码或工具接口。观察者不抢答；用户主动求助时记录具体卡点与帮助次数。首次授权和真正的身份验证另记，不混为可消除的失败。

完成后请参与者找到保存结果，再从原对话做第二次修改。用三个问题回访：刚才哪个地方最不确定？如果明天手机不在身边，你会从哪里开始？你如何判断 AI 确实做完？不询问笼统的“喜欢吗”。

原始录像和聊天只在经同意的私有目录保留；公开问题描述去除身份、内容和凭据。观察到的问题按阻断任务、需要帮助、可自行恢复排序，同一缺陷修复后只复测相关路径。

## 手动与 AI 对照

选同一任务、相同已有 App、相近资料长度和账号条件；先写清结果要求。分别记录从接单到核对结束的时间、结果是否完整、必要确认、人工补救次数。任务顺序交替，避免把用户第二次熟练操作全算成产品收益。

人工与 AI 任一方没有核对结果，就不计算“省时”；仍报告该次未完成。AI 较慢也照实记录，用户实际占用时间可另记，但不能用总耗时替代或混算。样本量、版本与设备范围必须同时出现。

## 有界恢复检查

| 情况 | 期望结果 | 本轮边界 |
| --- | --- | --- |
| 邀请未批准或过期 | 返回实际核对码与期限；过期说明重新邀请，未知结果先查原身份 | 不因过期删除已批准连接；不重置长观察 |
| 手机暂时断网 | 显示恢复中，恢复后用原连接重新观察 | 先用一分钟检查，再诊断；不无限循环同一失败 |
| 操作请求返回未知 | 先核对实际结果 | 不重发可能已经发送、保存或提交的动作 |
| 另一 AI 持有任务 | 清楚显示交接状态 | 不借测试抢占别人的真实任务 |
| 租约过期、断线或被撤销 | 不再显示旧 AI 正在接手 | 用户停止或撤销后不自动恢复 |
| 画面受保护或系统验证 | 显示真实限制与可执行下一步 | 不将所有权限弹窗都当成必须本人；不绕过真正身份验证 |

优先复用已有故障测试和版本证据。只有改动影响对应行为或发现新失败才补验，不为文案改动增加重启、72 小时或整套协议验收。

## 最少数据的体验统计

`python3 tools/experience_review.py /private/review.json` 只读本地、输出汇总，不联网、不接触手机。人工审阅后录入分阶段结果，不自动采集截图、App 名称、任务正文、邀请码、账号、设备标识或 AI 对话。原始内容不应放进这个文件，也不应提交到公开仓库。

输入示例是**合成数据**，不能作为实测证据：

```json
{
  "schema": "airtap-experience-v1",
  "synthetic": true,
  "attempts": [{
    "id": "case-example",
    "journey": "first_use",
    "ai": "muse",
    "version_code": 77,
    "last_setup_stage": "invitation_sent",
    "task_started": false,
    "result_verified": false,
    "task_seconds": null,
    "manual_seconds": null,
    "manual_verified": false,
    "required_confirmations": 1,
    "remedial_interventions": 0
  }]
}
```

`journey` 为 `first_use` 或 `returning`；后者的 `last_setup_stage` 用 `null`。首次阶段依次为 `arrived / installed / permissions_ready / invitation_sent / approved`，只填实际到达的一步，不能由复制按钮推断邀请已送达。`ai` 为 `muse / instinct / other`。`version_code` 记录实际版本；尚未安装或未读到时用 `null`，这些样本仍保留，不能用官网推荐版本冒充实测版本。时间只填实测正秒数，未知用 `null`；不要填 0 冒充瞬时完成。`required_confirmations` 统计初始授权及真正系统验证，`remedial_interventions` 统计为了救回任务额外叫人帮助的次数。

核心计数是“结果已核对且无需补救性人工介入的任务数 / 实际开始的任务数”。未完成、失败和仍未知的已开始任务留在分母；另报在接入阶段退出的人数。没有样本时返回 0/0，不宣传 100%。人工对照仅统计双方结果均已核对且计时存在的配对样本，报告中位时间差。默认不提供夸大的总体成功率结论。

## 两条视频的补录要求

- **安装视频**：当前版真实手机从正常安装、系统授权到邀请，切到实际 AI 对话展示申请和六位码，再切回手机批准，最后回对话完成首件任务。每次切换保留相邻动作，等待可倍速并标明；不能把已配对手机剪成首次安装。
- **使用视频**：先展示用户提出有价值的完整任务，再看真实手机跨 App 操作，回到 AI 汇报，最后用手机重开结果作结。可选“筛选远程岗位并保存三份申请草稿”或“公开资料整理成内容草稿”；保存、申请提交与公开发布必须准确区分。

无声录制，保留真实失败和自行恢复，不靠字幕虚构 AI 对话。新素材完成脱敏、人工逐段检查后，才替换公开视频。现有旧版视频继续明确其版本和非首装范围。按原真机观察结束后的录制窗口进行，不为补镜头中断观察。

方法参考：[Apple Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding)；[NN/g：定性小样本与定量研究的区别](https://www.nngroup.com/articles/5-test-users-qual-quant/)。
