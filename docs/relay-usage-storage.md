# 中继逐设备用量存储

候选实现将每日请求数、命令数和预留响应字节从整份设备登记表中分离，按 `usage:<device_id>` 保存。每次鉴权成功的计费检查只更新这一台设备的计数，不复制或重写其他设备的登记数据。计数仍使用同一个 AdmissionRegistry 的串行检查及持久化；这不是目录分片，也不代表 1000 台并发能力已经验收。

首次访问某台设备时，若独立计数还不存在，就使用登记表中的原有计数。之后独立计数具有优先级，重新登记和目录写入不能覆盖它。日期切换后按原规则重置当天计数；鉴权、停止控制、额度拒绝和未知设备检查仍在前。注销将终止登记状态和删除该设备的独立计数放在同一个存储事务中。

SQLite-backed Durable Objects 也支持这里使用的异步 key-value 存储和事务，见 [Cloudflare 存储说明](https://developers.cloudflare.com/durable-objects/api/legacy-kv-storage-api/)；不是 Workers KV 的最终一致性计数。

## 验证

`relay/service/tests/usage-storage.mjs` 使用真实本地 workerd 和 SQLite 存储，覆盖旧计数迁移、并发争抢额度、错误鉴权、额度边界、存储故障、进程重启、跨日重置、注销和控制关闭。测试注入入口只存在于本地 fixture，不导出到生产 Worker。

1000 条合成登记记录下，100 次成功用量更新产生 100 次逐设备写入、0 次登记整表写入。它验证了写入范围，不是云端压测、吞吐保证或账单测量。计数仍每次持久化，没有把额度检查改成可能丢失的内存缓存。

## 部署及回退

无需更换设备 ID、凭据、中继地址或配对。部署前后应保留同一组 Durable Object bindings；候选改动本身不代表已经部署到公共中继。

**回退其他业务改动时，保留这段逐设备计数读写代码。** 旧版本只读取登记表内的旧计数，直接整包回退可能少计当天已用额度。若确需回退到不认识独立计数的版本，必须先关闭控制入口并停止正在进行的请求，在维护过程中把每台设备最新独立计数合回登记表，核对完成后才能启用旧版本；当前不提供对外 HTTP 迁移接口。不能通过重新登记、换命名空间或重建数据库来规避迁移，因为那会破坏已有状态。
